## Tier 2 plan (structural, before the next feature wave)

1. **Versioned DB migrations** (S). `server/db.js` is one monolithic
   `migrate()` — idempotent DDL + `addColumn` helper + a data-repair `UPDATE
   sites SET status…` that runs every boot. No `schema_version`, no
   transactions per step (better-sqlite3 autocommits per statement; a
   mid-migration crash leaves partial schema that `IF NOT EXISTS` papers over).
   Fix: `PRAGMA user_version` + ordered migration functions, each in a
   transaction; fold the per-boot repair and addColumn calls into numbered
   steps. Do FIRST — rooms-from-SQLite and timelines-to-SQLite both add tables.
2. **Rooms map from SQLite** (L — the wall). Room identity still lives in
   `rooms.config.js`; rooms created in Admin → Campuses get
   `hasServerRoom:false` ("wired per room in rooms.config.js",
   Settings.tsx:1391-1396, index.js:741-746). Everything gates on the static
   map: endpoints (`rooms[req.params.id]`), autostart watchers
   (showManager.js:549-557 — started once at boot for a boot-static room set),
   connectivity seeding. Fix: build the `rooms` map from `site_rooms` +
   `room_connectivity` at boot; `rooms.config.js` becomes seed-only; watcher
   add/remove lifecycle for DB-created/deleted rooms. Blocks "more rooms
   without redeploying" (Youth Room/Chapel browser go-live).
3. **Split index.js into routers + extract mode service** (M). All ~50 routes
   inline (912 lines). Lockout-override check duplicated verbatim
   (index.js:204-209 vs 410-415); `applyMode` + in-memory `mockState`
   (index.js:80-81, 227-233) is domain state in the HTTP file — mock rooms
   forget their mode on restart while shows survive. One router per domain
   (rooms/modes, shows, events+checklists, auth/stations/users,
   config/connectivity, system) + `roomModes.js` owning applyMode/mockState/
   lockout check.
4. **Fake ProPresenter + Companion test servers** (M). companion.js: ZERO
   tests (the module that presses physical buttons — timeout, non-OK throw,
   variable URL-encoding). PP network fns all untested: readActive,
   readPlaylistItems, readSlide, readTimers, pollRunState. The fake-server
   pattern exists (smaart.test.js:9-84, rta.test.js:8-41) — extend it, then
   on top: autostart end-to-end (PRODMESH_AUTOSTART_TEST=1; transition onto
   startItemId starts show; PP-quirk null-baseline handling at
   showManager.js:534-538), restoreShows() boot recovery (corrupt-file skip,
   startedLogging restore), SSE stream contract (initial state event,
   broadcast on start, watcher teardown on last disconnect vs retention while
   show active), mode-route 502 branch (index.js:215-222) + state fallback
   (index.js:181-192).
5. **Form primitives + useDraft + split Settings.tsx** (M, can land
   panel-by-panel). Settings.tsx is ~20 components/1,900 lines; the labeled
   field `<label className="lfield">…` pattern is copy-pasted 37×; four
   near-identical draft/save state machines (PcServiceTypes/Analysis/
   Companion/ProPresenter editors) + variants in useChurchDraft and
   StationEditor; the campuses__head header+save block appears 6×; move/remove
   icon-button triplet 5×. Build `src/components/form/`: Field (label + control
   + inline error + width prop killing the six `!important`s in
   settings.css:648-661), TextInput/NumberInput, ColorInput, FormRow (CSS grid
   replacing flex-wrap soup — the Companion mode row is 8 fields + checkbox +
   3 buttons needing ~1100px in a 900px container, no media queries),
   SaveBar (dirty/busy/auto-clearing success/red error), EditorSection.
   Reference standard = IdentityDialog's field language. Then split panels
   into `src/pages/admin/` one file each. Also: dirty-navigation guard
   (no editor warns before discarding edits).

## Tier 3 plan (ride along with roadmap features)

6. **Integration health surface** (S-M — do FIRST when Calendar work starts).
   Silent `.catch(() => [])` is the house style for Planning Center
   (index.js:243, 307; showManager.js:266, 459-469; pp-playlist route) — an
   expired PC token degrades the whole app to mock-looking data with no log
   line. Per-integration status registry (lastSuccess/lastError/consecutive
   failures) on `/api/system/health`; log+count failures. Parallelize
   `/api/services` (index.js:252-265 — sequential per-room awaits, worst case
   rooms × 6s when PC is slow; use Promise.all like upcomingForRoom).
7. **Frontend query cache** (M — build WITH the Calendar UI, not before).
   Every page refetches on mount; getRooms() fetched independently by
   StationsPanel/SchedulesPanel/RoomStatus+; getAuthStatus() in AppShell +
   Settings + every auth-changed event; six independent setInterval loops
   (RoomStatus 4s, ServiceReport 5s, server log 5s, RoomCard/ServicePanel/
   Services); invalidation via stringly window events (prodmesh:auth-changed
   etc., api.ts:83-108). TanStack Query or a ~100-line useQuery(key, fn,
   {pollMs}) of our own (npm dep is fine — LAN-first only bans runtime CDN).
   Also fix api.ts inconsistencies: getAuthStatus/getSettings never check
   res.ok (a 403 there never triggers the login dialog).
8. **Timelines → SQLite + per-show summary rows** (M — before Analytics).
   `/api/history` calls timeline.listAll() TWICE per request (index.js:123,
   125), re-reading/parsing every JSON timeline file, then splStore.aggregate
   (full sample scan) per instance. Write a summary row at endShow;
   Analytics becomes one indexed query. Add spl_samples retention/rollup
   (~4,500 rows/show, no policy). Consider shows/timelines fully in SQLite.
9. **Operator-surface UI tests** (M). RunOfShow.tsx (368 lines) and
   RoomStatus.tsx (233) have ZERO tests. Highest value: show-identity check
   (isThisShow planId+timeId — regression double-starts shows), override-PIN
   flow (OverrideRequiredError → "Incorrect override PIN"), Prev/Next

   zone thresholds (>= limit red / >= target amber), countdown source
   priority (PP timer only when state==='running'). Plus api.ts unit tests
   with mocked fetch (header attachment, override_required →

### Resolved since the review

Taken off the list above once they were verified fixed on `main` (the #41
audit, 2026-09-10), and kept here so the record says where each one went.

- Swallowed programming errors behind the Planning Center fallbacks, the
  autostart loop's bare catch, and onPoll errors showing ProPresenter as
  disconnected: transport failures are now tagged as outages, and everything
  else is logged with its stack (`health.js` `survive()` / `unexpected()`,
  `68020fa`).
- Two parallel auth systems: gone, the admin PIN is the `admin` account's PIN
  (ADR 0012).
- A multi-room wall exhausting the ~6 connections per origin: one
  `EventSource` per tab over a multiplexed `/api/stream?topics=` (ADR 0010).
- `broadcast()` writing to every response unconditionally: the function no
  longer exists.
- The Planning Center cache never evicting: bounded by `CACHE_MAX` plus
  `prune()`.
- `loginFailures` never pruning: bounded by `FAILURE_CAP` plus eviction.
- RoomStatus polling the mode at 4s while show state used SSE: both are SSE.
